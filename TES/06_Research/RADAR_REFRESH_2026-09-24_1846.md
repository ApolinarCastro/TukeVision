### Material change

Frigate commit `9664d9ce` fixes a failure mode relevant to TukeVision observability: acknowledgement is episode-scoped rather than permanent dismissal, repeated detector failures can become visible again, high FFmpeg/detect CPU warnings become episodic notices, and concurrent status problems no longer overwrite one another because they share the same millisecond timestamp identifier.

### TukeVision problem affected

A recovery/health UI can become epistemically false-green if an operator acknowledgement suppresses later recurrences, or if simultaneous independent problems collide into one UI identity. This affects operator truth during decoder/detector recovery and resource-pressure episodes.

### Gate / capability

- Gate: operational observability / physical recovery validation.
- Capability: recurrent-fault visibility, independent fault identity, episode-aware acknowledgement.
- Risk: notification fatigue if recurrence identity is too granular; permanent mute can conceal a persistent condition if not governed.

### Minimum benchmark

1. Raise two distinct health faults in the same update interval; both remain independently addressable.
2. Acknowledge fault A; it disappears for the current episode.
3. Clear A, then reproduce A; it must become visible again.
4. Verify mute semantics, if ever implemented, are explicit and auditable rather than equivalent to acknowledgement.
5. Verify high CPU/decoder pressure episodes have start/clear/recur behavior tied to measured telemetry.

### Next gate

Before changing operator notice semantics, compare the existing TukeVision behavior against the benchmark above. If current behavior already satisfies it, classify `YA_RESUELTO`; otherwise adapt the episode-scoped acknowledgement pattern without importing Frigate code.
